# Pudding Lab — 可行性评估与方案设计

日期：2026-09-05。状态：设计阶段，尚未安装依赖、编写应用或运行 GPU 验证。

## 1. 结论与范围

可以实现：以 Three.js + WebGPU 制作可拖拽、有体积感、释放后弹跳晃动的布丁，并沿用参考图的编辑式排版和实验台氛围。

推荐最终架构是 **WebGPU 渲染 + CPU 上的小规模 XPBD 体积软体模拟**。WebGPU 用于真实的三维渲染与节点材质；本需求只有一个软体，不必把约束求解全部搬到 GPU。CPU 求解是本方案的正式选择，不是待替换的临时实现。

本轮交付：本方案和 `layout.svg` 布局草图。下一轮才进入项目初始化、技术验证及完整实现。

默认假设：单页交互作品、单个布丁、桌面体验优先、移动端响应式；无后端、无账号、无部署。截图用于视觉参考，其中的文案、物理单位、视频播放器控件均不视为必须实现的指令。

## 3. 可行性与难点

| 能力 | 评估 | 关键工作 |
| --- | --- | --- |
| 参考版式与响应式 | 高可行性，低难度 | HTML/CSS 与三维舞台分离 |
| 美味的布丁材质 | 高可行性，中难度 | 控制透光量、焦糖厚薄感、反射环境与曝光 |
| 拖动、拉伸、释放与回弹 | 可行，中高难度 | 局部抓取约束、体积约束、碰撞、阻尼调校 |
| 强烈形变仍保持平滑 | 可行，中高难度 | 低模驱动高模、法线更新、限制四面体翻转 |
| 60fps | 目标，尚未验证 | 指定测试设备后，实测求解、法线更新与透光渲染开销 |
| 全 GPU 软体 / FEM | 技术上可行，高难度 | 约束并行冲突、缓冲区布局、拾取与调试成本增加 |

Three.js 官方 WebGPU 文档提供节点材质与 TSL 路径，并明确部分旧 WebGL 定制方式不适用。实现时使用 `three/webgpu`、`three/tsl`，不沿用 `ShaderMaterial` 或 `onBeforeCompile` 配方。[官方说明](https://threejs.org/manual/en/webgpurenderer)

官方 Compute Geometry 示例展示了弹性恢复和指针作用，但其逐顶点回归原位的方式不等于体积软体；本项目不能直接据此宣称已有落地碰撞或体积守恒。[示例源码](https://raw.githubusercontent.com/mrdoob/three.js/dev/examples/webgpu_compute_geometry.html)

浏览器必须运行于支持 WebGPU 的环境和安全上下文，实际能否获取 adapter/device 要在目标设备确认。[MDN WebGPU](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)

## 4. 技术路线比较

| 路线 | 适用情况 | 本项目决定 |
| --- | --- | --- |
| 阻尼振子 + 顶点位移 | 固定姿态展示、轻点晃动 | 不作为核心：难以自然支持局部提拉与落地 |
| CPU XPBD + WebGPU 渲染 | 一个可抓取、可回弹的软体 | 推荐：成本可控，拾取与调试直接 |
| GPU Compute XPBD / FEM | 大规模软体，或明确要求全部 GPU 求解 | 当前范围不采用 |

XPBD 是带柔顺性约束的实时模拟方法，适合将形变程度、体积保持和抓取统一处理。本项目采用边长/形状约束与四面体体积约束，不把它宣传为经过材料标定的 FEM。[XPBD 原论文](https://matthias-research.github.io/pages/publications/XPBD.pdf)

技术栈：Vite + TypeScript + Three.js + 原生 HTML/CSS，使用 pnpm 锁定依赖。单页面板不引入 React 或全局状态库。初始化时确认当前稳定版本、引擎要求和相关类型，提交锁文件；本轮不预填未经验证的版本号。

## 5. 软体与几何设计

1. 程序化生成一个封闭、无自交的布丁体积笼，初始预算 300–800 个节点、约 1,000–3,000 个四面体；这些是原型预算，需实测校准。
2. 使用结构化体积网格映射到模具轮廓，统一剖分方向；构建后验证共享面一致、四面体有符号体积为正、没有退化单元。
3. 可见表面初始预算 8,000–20,000 个三角形。初始化时保存每个表面顶点所属四面体及重心权重，随体积笼变形，避免逐帧重新求绑定关系。
4. 焦糖区域与主体共用形变数据，通过材质分组/表面遮罩区分；边缘少量凝固垂坠轮廓在建模时生成，避免独立壳层穿插，不模拟流动液体。
5. 每步处理重力、弹性约束、体积约束、地面碰撞与局部抓取，更新速度并施加随时间步一致的阻尼。
6. 初始采用 120Hz 固定物理步，单步 4–8 次约束迭代作为调参起点；渲染采用插值。限制单帧补步次数，失焦后暂停，恢复时清空积累时间。
7. 抓取区域使用权重衰减，限制目标移动速度与最大拉伸，降低四面体翻转风险。初版支持有界形变，不包含撕裂、切割、任意打结和完整自碰撞。
8. 每帧随可见表面更新法线，并更新用于射线拾取的包围范围；阴影使用相同形变后的几何，避免高光和影子停留在原始姿态。

通过 `Firmness` 控制弹性约束柔顺性，通过 `Damping` 控制速度衰减；体积保持独立设置，以便布丁变软但不明显泄气。滑块采用无单位体验值，未经本构关系与尺度标定不显示 kPa。

## 6. 材质与渲染

使用 `MeshPhysicalNodeMaterial`。蛋奶部分以漫反射为主，适量透光、偏暖的吸收颜色、适度粗糙度；焦糖使用较低粗糙度和克制的清漆层。参数通过同一场景实测调色，不把截图上的高透明度直接套到蛋奶布丁。[材质 API](https://threejs.org/docs/pages/MeshPhysicalNodeMaterial.html)

环境照明采用程序化柔光棚环境，配合主光、填光与接地阴影。先用曝光、色调映射和稳定的反射形状达到食欲感；屏幕空间散射、色散、多层折射与焦散不列入首版，避免效果与性能同时失控。

直接顶光导致塑料感、过强透光导致玻璃感，是主要视觉风险。验收要同时看静止截图和运动中的高光，而不能只看线框弹跳是否正确。

应用显式验证原生 WebGPU 后端：Three.js 自带自动 WebGL 回退，但本项目不将回退结果标成 `WEBGPU · LIVE`。无法初始化时显示清晰的不可用状态和重试入口；设备丢失时停止动画并提供恢复操作。

## 7. 交互契约

| 操作 | 预期行为 |
| --- | --- |
| 初次进入 | 布丁轻落地，压扁、回弹、逐渐静止；减少动态效果偏好开启时不自动演示 |
| 点击 / 轻触 | 点击命中位置产生轻微局部冲量，周围跟随晃动 |
| 按住拖拽 | 抓住命中区域，在屏幕朝向平面内提拉；主体其余部分受重力影响 |
| 松手 | 释放抓取约束，保留合理速度，回落并衰减晃动 |
| Give it a nudge | 施加可重复的横向冲量，可通过键盘按钮触发 |
| Vanilla / Berry / Matcha | 平滑切换颜色、焦糖/酱层材质预设；保留当前模拟状态 |
| Firmness / Damping | 实时改变手感；使用有标签的原生 range，支持键盘 |
| ¼ speed | 改变模拟时间累积速率，物理固定步长保持不变 |
| Pause | 暂停模拟与施力；仍允许颜色和面板操作；取消当前抓取 |
| Show mesh | 显示实际体积笼/表面线框，清楚标识显示对象 |
| Reset | 恢复初始形状、零速度、默认口味和参数，并解除暂停、慢速与抓取 |

指针离开窗口、`pointercancel`、丢失捕获或切换页面时必须释放抓取。默认不启用左键旋转相机，避免与抓布丁竞争；核心展示保持固定构图。

左下可显示 `VOLUME`（当前体积 / 静止体积）、`MOTION`（归一化速度水平）和当前状态。读数从实际模拟计算，每秒刷新约 5–10 次；不抄录参考图的质量与能量数值，不显示没有定义的 mJ。

## 8. 模块边界

拟定源码结构：`src/main.ts` 负责生命周期；`scene/` 负责相机、光照和 WebGPU；`pudding/` 负责建模、材质、表面绑定；`physics/` 负责固定步进与约束；`interaction/` 负责拾取和抓取；`ui/` 负责控件及读数；`styles.css` 负责版式。

数据流：指针/控件 → 应用状态及施力 → 固定步软体求解 → 表面插值与法线 → WebGPU 渲染。界面从状态读取，控件不直接访问求解器内部数组。

资源创建与释放成对管理；窗口 resize 更新布局、相机和渲染尺寸，重复初始化不能残留监听器或动画循环。

## 9. 实施顺序与验收门槛

### A. 最小完整技术验证

建立 Vite 工程，验证原生 WebGPU 初始化；用最终求解路线做一个可拖拽、可落地的低模布丁，加真实材质与阴影。先确认整个循环可运行，再扩大网格和增加视觉细节。

通过条件：本机浏览器真实 WebGPU 渲染、无验证错误；抓取释放有效；形变后的法线、阴影和拾取一致。若 WebGPU 初始化失败，明确记录环境原因。

### B. 完成视觉与控制

替换为最终模具几何、调校奶油/焦糖材质，完成参考布局、三种口味和全部控件，并针对鼠标、触控、键盘与窄屏调整。

通过条件：1440×900 桌面和 390×844 窄屏无主体/控制卡误遮挡；控制状态一致；默认扰动后有至少两次可辨回摆并约 2–5 秒内显著衰减。该时间是体验目标，需调参确认。

### C. 稳定性与性能

自动验证真实行为边界：确定性冲量后节点保持有限；有界交互下无四面体翻转；默认参数稳定后体积误差目标 < 3%；地面穿透不超过静止高度的 1%；暂停/重置/取消抓取正确。测试使用固定步进，不依赖睡眠等待。

浏览器验证：滑块、口味、暂停、慢速、重置、键盘和移动布局；持续拖拽与释放 60 秒；后台恢复不会突然爆炸。无头环境若缺少 WebGPU，不据此声称渲染通过。

性能目标：在记录了浏览器、GPU、视口与 DPR 的参考设备上，1440×900、DPR 上限 1.5 时平均接近 60fps，95% 帧时间不高于 20ms；移动端目标至少 30fps。均为待测目标。若不达标，优先降低像素比、阴影分辨率和透光成本，再依据实测调整网格预算。

交付时运行类型检查、生产构建、物理行为测试及真实浏览器检查；记录跳过项、帧时间、已知限制与启动命令。
